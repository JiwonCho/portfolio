01 / Summary

한 줄 요약 (직무별 3안)

지원하는 포지션에 따라 강조점이 달라집니다. 네 가지 버전 중 하나를 골라 쓰세요.

A · 프론트엔드 엔지니어 (일반)

여행 커머스 서비스(투어비스·프리비아)의 상품 탐색–예약–결제 전 구간을 담당하는 프론트엔드 개발자입니다. Next.js·TypeScript 기반 pnpm 모노레포 두 곳과 Nuxt 기반 예약·결제 서비스를 함께 다루며 투어&티켓 상품상세·옵션선택 플로우를 재구축했고, SEO·LCP·로깅 규격화까지 서비스 품질 전반을 맡고 있습니다. 4년 7개월간 1,335건의 티켓을 처리했습니다.

B · 도메인 전문성 강조 (커머스/여행)

국내 최대 여행 커머스 두 개 브랜드에서 상품 옵션·재고·다이나믹 프라이싱·취소환불 정책처럼 규칙이 복잡한 커머스 도메인을 프론트엔드에서 구현해 왔습니다. 유니버설 스튜디오 재팬 패스처럼 회차·입장시간·어트랙션 조합이 얽힌 상품군을 전담했고, 네이버여행·지마켓·구글 TTD·GetYourGuide 등 외부 채널 연동도 함께 담당했습니다.

C · 성장 서사 강조 (퍼블리싱 → 개발)

퍼블리싱으로 시작해 프론트엔드 엔지니어링으로 역할을 확장했습니다. 마크업·운영 대응(2022–2023)에서 공용 컴포넌트 체계·컴포넌트 아키텍처 설계(2024), 기능 단위 FE 개발(2025), 아키텍처·성능·AI 기능(2026)으로 단계적으로 범위를 넓혔고, 현재는 서버 전용 코드 분리, 로그 포맷 규격화, AI 에이전트용 기술 문서화까지 맡고 있습니다. 그 사이 Braze 인앱·인웹 메시지 템플릿처럼 마크업 감각과 스크립트 설계가 동시에 필요한 과제는 기획부터 빌드 환경까지 단독으로 구축·운영했습니다.

D · 시니어 · 리드 지원용 (아키텍처 강조)

기능 구현을 넘어 여러 개발자가 따를 구조를 정의해 온 프론트엔드 개발자입니다. 프리비아 해외패키지 신규 구축에서 App Router의 서버 컴포넌트·비즈니스 로직 컴포넌트·순수 UI를 나누는 3계층 컨벤션을 설계해 클라이언트 경계를 한 겹으로 고정했고, 서비스별로 중복되던 컴포넌트를 5개 앱이 공유하는 공용 디자인 시스템으로 승격했습니다. 투어비스에서는 그룹상품의 상태 격리, 취소·환불 정책의 표시 변환 계층, 서버 전용 코드 분리처럼 경계를 긋는 작업을 반복해 맡았고, 설계 판단은 매번 계획서·가이드 문서로 남겨 팀의 기준으로 만들었습니다.

15Braze 커스텀 인앱·인웹 메시지 템플릿 시스템 구축

배경
Braze는 고객 참여·마케팅 자동화 플랫폼으로, 앱·웹 화면 위에 인앱 / 인웹 메시지를 띄웁니다. 기본 제공 템플릿은 브랜드 톤과 배치 규칙을 맞출 수 없어 Custom HTML 메시지로 직접 만들어야 했습니다.
Custom HTML 메시지는 Braze가 만든 iframe 안에서 실행되는 독립 문서입니다. 외부 CSS·JS를 참조할 수 없어 한 파일에 전부 인라인되어야 하고, 클릭 성과 집계와 닫기는 Braze 브릿지 API를 통해서만 가능하며, iframe의 크기·위치는 자식 문서가 부모를 거꾸로 제어해야 합니다. 이 제약 위에서 브랜드 두 개 × 메시지 유형 네 개 × 노출 상황 두 개를 감당할 구조가 필요했습니다.
구현
  • 템플릿 빌드 파이프라인을 직접 구성했습니다 — Nunjucks + Gulp 5 + SCSS. 레이아웃 · 컴포넌트 · 스크립트 · 스타일을 각각 부분 템플릿으로 쪼개고, 브랜드·유형·상황 조합마다 필요한 조각만 조립해 자체 완결 단일 HTML로 뽑아냅니다. Braze 대시보드에 붙여넣을 때 외부 참조가 하나도 없어야 하므로 CSS·JS를 전부 인라인합니다.
  • 부모 iframe 제어 — Braze가 생성한 메시지 iframe을 자식 문서에서 최상위 window로 거슬러 잡아 뷰포트별로 재배치합니다. 750px 미만은 전체 화면 고정, 이상은 브랜드별 우측 하단 오프셋 (투어비스 318px / 프리비아 395px)으로 다르게 앉힙니다. 콘텐츠 실제 높이를 측정해 iframe 높이를 맞추고, 그 값을 CSS 변수로 부모 문서에 되돌려 기존 스낵바·플로팅 요소와 겹치지 않게 했습니다.
  • 대시보드 프리뷰 대응 — 마케터가 Braze 대시보드에서 미리 볼 때는 부모 문서 접근이 막힙니다. cross-origin 접근 시 예외가 나는 성질을 이용해 대시보드 환경을 판별하고, 그때는 자기 자신을 루트로 삼도록 폴백을 뒀습니다. 로컬 파일 프로토콜에서도 같은 경로를 탑니다. 제작자가 대시보드에 올리기 전에 로컬에서 그대로 확인할 수 있는 것이 이 구조의 핵심 이점입니다.
  • 초기 깜빡임 제거 — 레이아웃 계산 전에 노출돼 메시지가 튀는 문제를, 초기 투명 처리 후 아이콘 이미지 프리로드 완료 → 크기 계산 → 클래스 부여 → 페이드인 순서로 잡았습니다.
  • Braze 기본 동작 오버라이드 — Braze는 메시지 표시 중 본문 스크롤을 잠급니다. 배너·스낵바형은 스크롤이 되어야 하므로 해당 클래스를 걷어내고, 루트 클래스도 커스텀 애니메이션 세트로 갈아끼웠습니다.
  • 브릿지 연동 — 브릿지 준비 이벤트에서 data-button-id가 붙은 요소에 핸들러를 걸어 클릭을 Braze에 기록(성과 집계)하고, 퇴장 애니메이션 300ms 뒤에 메시지를 닫습니다. 일반형과 모달형은 애니메이션 시퀀스가 달라 스크립트를 분리했습니다.
  • 노출 제외 규칙 — 프로모션·기획전 페이지 위에 메시지가 겹치면 안 돼서, 브랜드별 URL 키워드 차단 목록으로 해당 경로에서는 렌더를 건너뛰고 스크롤 잠금도 되돌립니다.
  • iOS 대응 — vh 단위가 iOS 주소창에 따라 튀는 문제를 실제 뷰포트 높이를 CSS 커스텀 프로퍼티로 주입해 해결했습니다.
  • 운영 편의 — 템플릿 목록을 JSON으로 관리해 인덱스 페이지를 자동 생성합니다. 브랜드 · 유형 · 상황별로 정리된 표에서 완료/수정중/대기 상태와 미리보기 링크를 한눈에 보고, 마케터·기획자가 링크만으로 확인할 수 있습니다. 배포는 산출물 묶음으로 전달합니다.

배경
프리비아 해외패키지를 Next.js App Router로 신규 구축하는 프로젝트에 초기 구조 설계 단계부터 참여했습니다. App Router에서는 서버 컴포넌트와 클라이언트 컴포넌트가 한 트리에 섞이는데, 규칙 없이 만들면 'use client'가 위쪽으로 번져 서버 렌더링 이점이 사라지고 같은 UI가 서비스마다 중복 구현됩니다. 그래서 컴포넌트의 역할을 이름으로 강제하는 규칙을 먼저 세웠습니다.
구현
  • 3계층 분리 — 이 프로젝트의 핵심 특징입니다.
    • SC (Server Component) — async 서버 컴포넌트. 데이터 패치만 담당하고 재검증 주기를 선언합니다. 패치 함수는 *.fetch.ts로 같은 폴더에 붙여 두어, 이 화면이 무슨 API를 쓰는지 파일만 봐도 드러납니다.
    • BLC (Business Logic Component) — 'use client' 경계. SC가 넘긴 초기 데이터를 상태로 받아 사용자 상호작용과 도메인 로직을 담당합니다. 추가 조회는 *.action.ts 서버 액션으로, 복잡한 로직은 use*BLC.ts 훅으로 다시 분리합니다.
    • UI 컴포넌트 — 상태도 패치도 없는 순수 프레젠테이션. 공용 디자인 시스템 패키지에 두고 props로만 제어합니다.
    덕분에 'use client' 경계가 BLC 한 겹에서 멈추고, UI는 어느 서비스에서든 재사용되며, 서버 데이터 흐름이 SC에 모입니다. 파일명만 봐도 그 컴포넌트가 무엇을 해도 되고 무엇을 하면 안 되는지 알 수 있는 게 이 규칙의 목적이었습니다.

  • Lit 기반 웹 컴포넌트 퀵서치 — 패키지 검색창을 다른 서비스에서도 써야 해서, React 트리 밖에서 동작하는 웹 컴포넌트로 따로 빌드했습니다. Rollup으로 단일 번들을 만들어 정적 스크립트로 복사하는 빌드 단계를 두어, React를 쓰지 않는 페이지에도 스크립트 태그 하나로 삽입됩니다. 최근 검색·키워드 추천·출발일 캘린더 필터·검색 조건 리스트를 각각 커스텀 엘리먼트로 나눴습니다.
